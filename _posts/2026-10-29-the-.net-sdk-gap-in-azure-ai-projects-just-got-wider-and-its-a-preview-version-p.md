There is no new flagship model to celebrate this week. No surprise API cutover, no fresh pricing table to panic over. What the last few days of SDK tracking *do* reveal is a quieter, more structural issue for .NET teams building on Azure AI Foundry: the Python, JavaScript/TypeScript, and Java client libraries keep shipping v2 releases on a monthly cadence, while the .NET line sits still.

According to the community release trackers that watch the four language SDKs, the October wave advanced Python and JavaScript/TypeScript from 2.4.0 to 2.9.0 and Java from 2.3.0 to 2.8.0. The same tracker states plainly: "The .NET v2 line and REST API versions are unchanged." A follow-up check dated 2026-10-28 confirmed JavaScript and Java shipped on October 19, with Python following a separate October 16 release — and no .NET movement in between.

If you are a .NET shop betting on Foundry, that sentence should make you sit up. Not because your code is broken today, but because the surface you are coding against is drifting away from the one everybody else is documenting, testing, and demoing.

## What's actually changing (and what isn't)

Let's be precise, because "SDK lag" is the kind of phrase that gets repeated until it means nothing.

The Azure AI Projects SDK is the client library you use to talk to Foundry projects: agents, deployments, connections, and the REST surface behind them. It ships in four languages. The v2 line is the current generation. What the trackers show is not that .NET is *missing a feature* — it's that the version *number* has stopped advancing while its siblings move several minor versions ahead.

Three things follow from that, and only one of them is urgent:

- **Feature parity is not guaranteed.** When Python and TypeScript jump five minor versions in a month, some of that is bug fixes and some of it is new capability. The .NET consumer cannot tell which from the version number alone.
- **Documentation skews to the fastest-moving SDK.** Samples, quickstarts, and blog posts tend to be written against the language the team ships first. That is rarely .NET.
- **Your REST fallback becomes load-bearing.** If a Foundry feature lands in the Python SDK before the .NET one, the .NET path is often "call the REST endpoint yourself and deserialize." That works, but it means you own the schema.

## The preview problem underneath the version gap

There's a second wrinkle in the Foundry SDK story that matters more than the minor-version count. According to Microsoft's July/August 2026 Foundry roundup, the .NET 3.0.0 line remained in **preview**, and hosted-agent management and runtime support differed by language. The same post notes that by end of August, `azure-ai-projects` 2.5.0 required Python 3.10+ and `openai>=3.0.0`, JavaScript/TypeScript raised its minimum to Node.js 22 in 2.3.0, and the Java line reached 2.4.0.

So the maturity ladder looks like this: Python and JS are shipping stable v2 releases on a monthly beat; .NET's next-generation line is still preview, with capability gaps that Microsoft itself flags as language-dependent. That is not a scandal. It is a planning input. If you are choosing a language for a Foundry workload that has to be production-grade in Q1, that asymmetry belongs in the decision, not in a footnote you discover in week six.

If you want to know where .NET actually stands rather than trusting a version string, pin your dependency and read the changelog for the specific package. Here's the pattern that pays off — a `PackageReference` you can actually reason about, plus the code that tells you at startup whether the surface you compiled against is the one that loaded:

```csharp
// Azure.AI.Projects — pin explicitly, then assert at startup.
// Do NOT let a floating version decide which Foundry surface you ship.

using Azure.AI.Projects;
using Azure.Identity;
using Microsoft.Extensions.Logging;

// In your .csproj:
//   <PackageReference Include="Azure.AI.Projects" Version="1.0.0-beta.1" />
// Replace the version with the one your changelog review actually approved.

var endpoint = Environment.GetEnvironmentVariable("FOUNDRY_PROJECT_ENDPOINT")
    ?? throw new InvalidOperationException("FOUNDRY_PROJECT_ENDPOINT is not set.");

var client = new AIProjectClient(new Uri(endpoint), new DefaultAzureCredential());

// Fail fast and loudly: log the assembly version that actually loaded.
// A floating reference can silently resolve to a different build than you tested.
var asm = typeof(AIProjectClient).Assembly;
logger.LogInformation(
    "Azure.AI.Projects loaded: {Name} {Version}",
    asm.GetName().Name,
    asm.GetName().Version);

// Any call below is only as stable as that version number.
// Verify it against the SDK release notes before you promote this build.
```

The point of the snippet is not the API call — it is the version assertion. In a world where the .NET line ships on a different cadence than Python and JS, "which build did production actually load?" is a question you want answered by a log line, not a post-incident archaeology dig.

## What to do about it, concretely

- **Pin, don't float.** Treat the Foundry client library like any other dependency with a moving surface: explicit version, reviewed changelog, deliberate bump.
- **Log the loaded assembly version at startup.** Cheap, permanent, and it ends the "but it worked on my machine" debate.
- **Check feature parity before you commit to a design.** If the feature you need is documented in Python only, budget for the REST path or pick a different language for that piece.
- **Watch the deprecation calendar separately.** The REST API versions and the SDK versions move independently, and a REST version bump can break a client library that "hasn't changed."
- **Don't read the version number as a maturity score.** A preview 3.0.0 line and a stable 2.9.0 line are telling you different things; the number alone won't say which.

## The takeaway

The Foundry SDK story this month is not a launch. It is a steady-state condition: three languages advancing in a coordinated wave, one holding position, and a preview line on the .NET side that Microsoft describes as language-dependent in capability. For .NET engineers, the correct response is not alarm — it is instrumentation. Pin your versions, log what loads, and check parity before you design around a feature that only exists in someone else's SDK.

Boring? A little. But boring is what you want from your dependency graph.
