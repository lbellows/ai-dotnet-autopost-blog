There's a quiet asymmetry in the Azure AI tooling stack right now. Python has moved to Azure AI Projects SDK v2 2.9.0, JavaScript to 2.9.0, Java to 2.7.0. The .NET client is still sitting on 2.1.0-beta.4 — its last dated v2 release — while a v3 prerelease line exists but is treated as out of scope by the trackers watching it. If your agent stack is C#, you are not on the same release train as the rest of the ecosystem, and you probably haven't been told.

This isn't a fresh announcement from this week. It's a slow-burning infrastructure gap that's worth a real conversation, because agent SDK version skew doesn't surface as a build error. It surfaces as a tool call that silently behaves differently in production.

## What actually shipped, and when

Let's be precise, because this is the kind of thing people get wrong. According to the foundry-docs SDK release trackers, JavaScript and Java shipped coordinated releases of Azure AI Projects SDK v2 on 2026-10-06 ([issue #1160](https://github.com/nicholasdbrady/foundry-docs/issues/1160)). A later tracker records Python advancing to 2.9.0 separately, with a changelog check logged on 2026-10-19 ([issue #1177](https://github.com/nicholasdbrady/foundry-docs/issues/1177)). Java remained at 2.7.0 while Python and JS moved on.

The .NET entry in those same trackers is the interesting part: it's explicitly flagged as remaining at its last dated v2 release, 2.1.0-beta.4, with newer .NET v3 prereleases treated as out of scope. The REST API underneath is also unchanged — Foundry REST remains at v1, with stable `2025-05-01` and preview `2025-05-15-preview` as of that October 19 check.

So the wire protocol is stable. The Python, JS, and Java ergonomic layers are marching forward. The .NET layer is parked on a beta.

## Why version skew in an agent SDK is worse than version skew elsewhere

For a normal REST client, a version lag means you miss a convenience method. You call the endpoint by hand, you move on. For an agent SDK, the lagging layer is typically responsible for things that are *not* on the wire:

- **Session and history management.** The Azure SDK for .NET release notes describe the removal of an internal `DEFAULT_FETCH_HISTORY_ITEM_COUNT` environment-variable read and ambient `TokenCredential` registration, changes that alter how conversation history gets fetched and how credentials get resolved.
- **Endpoint resolution.** The same notes describe `FOUNDRY_PROJECT_ENDPOINT` being demoted to a fallback for an unconfigured `ResponsesServer:Endpoint`, plus an HTTPS-in-host-environment check. These are the sort of config semantics that differ between SDK versions without changing the REST contract.
- **Agent and toolbox contracts.** The Foundry extension releases prepared on 2026-10-15 set `azure.ai.toolboxes` to beta.11 and `azure.ai.agents` to beta.20 ([PR #10491](https://github.com/Azure/azure-dev/pull/10491)). Those are the version pins that determine which agent-authoring features exist at all.

The upshot: two engineers on the same team, one writing Python and one writing C#, can point at the same Foundry project and get genuinely different behavior around history fetch, credential fallback, and agent authoring — while both believe they're "using the SDK."

## The two-path problem nobody documents in one place

There's a second axis of confusion here. Foundry lets you consume Claude models two ways: Azure-hosted or Anthropic-hosted. The September 2026 Foundry blog explicitly cautions that OpenAI client parameters should not be assumed to transfer unchanged, and that you should check each model's API and availability boundaries ([devblogs](https://devblogs.microsoft.com/foundry/whats-new-in-microsoft-foundry-september-2026/)). Combine that with an SDK that's several minor versions behind, and "read the changelog" stops being advice and becomes a job.

Worth noting for planning: knowledge cutoffs in that same September post are April 2026 for Astra and GPT-6.1 Sol, May 2026 for Luna, and GPT-6.1 Sol tool calls require the Responses API specifically. Those are capability constraints that don't care which language you write.

## What to actually do about it

**Pin and document your SDK version in the repo, not in someone's head.** If your C# service is on 2.1.0-beta.4 and a Python notebook in the same org is on 2.9.0, that discrepancy should be a line in a README, not a surprise during an incident.

**Treat the .NET v3 prerelease line as a deliberate decision, not a default.** The trackers explicitly separate it out. If you adopt it, you own the upgrade path.

**Test against the REST contract, not the SDK convenience layer.** Since Foundry REST is stable at `2025-05-01`, you can write integration tests that assert on the wire behavior you depend on, which survives SDK churn on any platform.

**Watch the config surface, not just the method surface.** `FOUNDRY_PROJECT_ENDPOINT` as a fallback, `FOUNDRY_AGENT_SESSION_GUID`, API version `2026-05-15`, and the HTTP/HTTPS host check are all environment-level behaviors. A config diff between SDK versions is where this bites hardest.

**If you're on a launch timeline, budget for the .NET path being slower.** The other languages shipped in a coordinated rollout in early October; .NET's most recent dated v2 release predates that baseline. That's a planning input, not a complaint.

## The honest summary

Nothing here is on fire. The REST API is stable, the models are available, and the .NET SDK works. But "works" and "is on the same release train as your Python and JS services" are different claims, and right now the second one is false for the Azure AI Projects .NET client. The fix isn't dramatic — pin your versions, test the wire contract, and stop assuming the SDK abstraction is language-neutral. It isn't, and it never was.
